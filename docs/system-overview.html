Target Allocation — คู่มือการทำงานของระบบ

ระบบกระจายเป้าหีบจากหัวหน้าทีมลงพนักงานขายรายคน แล้วส่งกลับเข้า Target Sun

1 · ระบบนี้ทำอะไร

โจทย์: Target Sun กำหนด เป้าหีบรวมต่อ SKU ของทั้งทีม มาให้ หัวหน้าทีม (Supervisor) ต้องแตกเป้านั้นลงไปว่า พนักงานขายคนไหนควรได้กี่หีบของสินค้าตัวไหน แล้วส่งผลกลับเข้า Target Sun

ทำมือไม่ไหวเพราะทีมหนึ่งมี SKU ระดับ 200–650 รายการ × พนักงาน 5–30 คน = หลายพันช่อง และต้องพอใจสองเงื่อนไขพร้อมกัน:

  • หีบต่อ SKU ต้องครบเป้า ห้ามขาดห้ามเกิน
  • มูลค่าเงินต่อคนต้องใกล้เป้ารายคน (เป้าเหลือง / yellow_target)

ระบบแก้ให้ด้วยการผสม สัดส่วนจากประวัติการขาย กับ Linear Programming แล้วให้หัวหน้าปรับมือทับได้ในจุดที่ต้องการ

3 · ขั้นตอนการใช้งาน 3 ขั้น

ขั้น 1 ข้อมูลตั้งต้น

เลือกทีม + งวด (เดือน/ปี) ระบบดึงพนักงาน เป้าหีบ ราคา และประวัติ แล้วเขียนลง cache ใน data/ ทุกไฟล์แยกตาม (ทีม, งวด)

ถ้างวดที่เลือกไม่มีเป้าใน TGA ระบบตอบ 409 และไม่ให้เข้าหน้าถัดไป

ขั้น 2 กำหนดเป้าเงินรายคน (ไม่บังคับ)

ปรับ เป้าเหลือง รายคนได้ ถ้าไม่แตะ ระบบใช้ค่าจาก Target Sun ตามเดิม มีช่องบันทึกเหตุผลกรณีเป้าโตติดลบ และหักลด BUI

ขั้น 3 กระจายหีบ

เลือกวิธี (เลือกได้มากกว่า 1 แล้วกำหนดว่าแบรนด์ไหนใช้วิธีไหน) กด เริ่มคำนวณ ได้ตารางผลลัพธ์ที่แก้ตัวเลขได้ แล้วดาวน์โหลด Excel หรือส่งเข้า Target Sun

4 · เครื่องกระจายหีบ

อยู่ใน backend/OR_engine.py — import แค่ pandas กับ logging ไม่แตะไฟล์ ไม่แตะเน็ต ไม่แตะฐานข้อมูล ทดสอบได้ในหน่วยความจำล้วน

วิธีกระจายที่เลือกได้

รหัสหลักการผ่าน LP?เห็นใน UI?
L3M ค่าเริ่มต้นสัดส่วนยอดขายเฉลี่ย 3 เดือนย้อนหลังใช่เห็น
L6Mสัดส่วนยอดขายเฉลี่ย 6 เดือนใช่เห็น
LYสัดส่วนเดือนเดียวกันปีที่แล้วใช่เห็น
PUSHผลักดันคนขายน้อย — ให้น้ำหนักกลับด้าน max − histไม่เห็น
EVENเกลี่ยเท่ากันทุกคนไม่ซ่อน
LPยึดเป้าเงินเป็นหลัก (baseline L3M)ใช่ซ่อน

ทั้ง 6 ตัวรองรับใน backend (VALID_STRATEGIES) แต่ EVEN และ LP ถูกคอมเมนต์ปิดไว้ใน frontend/index.html ชั่วคราว — UI จึงแสดงแค่ 4 ตัว ยิงผ่าน API ตรง ๆ ยังใช้ได้ทั้ง 6

ลำดับการทำงาน 6 ขั้น

1. _normalize_engine_inputs   ทำคีย์ให้อยู่รูปเดียวกัน · ปัดเป้าเป็น int · ยุบ SKU ซ้ำ
                              · ปฏิเสธถ้าหีบที่ล็อกรวมกันเกินเป้า SKU
        │
2. _proportional              แบ่งตามสัดส่วนประวัติ + เพดานกันกระจุก (mean × 3.0)
                              → ได้ baseline ที่ทุกขั้นถัดไปใช้อ้างอิง
        │
3. _lp_optimize (CBC)         ปรับให้มูลค่าเงินต่อคนใกล้เป้า ภายในรั้ว ±% จาก baseline
        │                     แก้ไม่ได้ → ใช้ผลข้อ 2 แทน (ตั้ง optimization_fallback)
        │
4. _greedy_revenue_balancer   โยนหีบทีละใบระหว่างคนที่เกิน↔ขาด ปิดช่องว่างที่เหลือ
        │
5. _enforce_even_skus_on_df   สินค้าใหม่ที่ติ๊กไว้ → บังคับแบ่งเท่าทุกคน
        │
6. validate_allocation_vs_targets   ประตู: ผลรวมต่อ SKU ต้องตรงเป้า ไม่งั้น 409

รั้วกันตัวเลขเพี้ยน

หัวใจคือ baseline จากประวัติ แล้วอนุญาตให้ LP ขยับได้แค่ในกรอบ %:

ประเภท SKUรั้วค่าคงที่
SKU หลัก (สะสมมูลค่าเป้าถึง 80% แบบ Pareto)±35%_TIER_FLEX_BAND_PCT
SKU รอง±12%_TIER_STRICT_BAND_PCT
ไม่เปิดโหมดหลัก/รอง±20%_DEFAULT_HIST_BAND_PCT
สินค้าใหม่ที่ติ๊กแบ่งเท่าล็อกตายตามค่าแบ่งเท่า—
คนที่ไม่มีประวัติ SKU นั้น (baseline 0)เพดาน ceil(เป้า ÷ คน × 3.0)ปิดเป็นค่าเริ่มต้น

ทำไมเพดาน baseline 0 ถึงปิดไว้

วัดกับข้อมูลจริง 8 ทีมแล้ว เปิดแล้วหีบย้ายที่ราว 2–3.5% ของทั้งทีม (ผลรวมต่อ SKU ยังตรงเป้าทุกกรณี แค่ย้ายจากคนไม่มีประวัติไปหาคนมีประวัติ) หัวหน้าทีมจะเห็นตัวเลขต่างทันที จึงถือเป็นการตัดสินใจเชิงนโยบาย ไม่ใช่บั๊ก

เปิดได้ด้วย ALLOC_ZERO_BASELINE_CAP=1 · ตัวคุมชั้นแรก (เพดาน mean×3, anchor term ถ่วงด้วยราคา, สมการผลรวมต่อ SKU) ทำงานอยู่แล้วทั้งหมด

ค่าที่หน้าเว็บส่งมาจริง

พารามิเตอร์ค่าความหมาย
tiered_allocationtrueเปิดโหมด SKU หลัก/รอง
tier_pct0.80SKU หลัก = สะสมมูลค่าเป้าถึง 80%
hist_balance0.35น้ำหนักยึด baseline ใน LP

ข้อควรระวังสำหรับคนแก้โค้ด — ชื่อตัวแปร LP

ห้ามเอา emp_id / sku ไปต่อเป็นชื่อตัวแปร PuLP PuLP ล้างเฉพาะอักขระใน "-+[] ->/" ซึ่งแปลง - เป็น _ ทำให้ ("A-B","C") กับ ("A","B_C") ได้ชื่อชนกัน → CBC พังเป็น PulpSolverError → ตกไป fallback แบบเงียบ ๆ ใช้ _vname() ที่สร้างชื่อจากเลขลำดับเท่านั้น

5 · กฎที่ระบบบังคับ

รายละเอียดเต็มอยู่ใน docs/ALLOCATION_INVARIANTS.md — ย่อไว้ที่นี่

#กฎบังคับที่ไหน
I1ผลรวมหีบต่อ SKU = เป้าหีบ เป๊ะ ๆ/optimize ตอบ 409 · ไม่เขียนไฟล์ ไม่สร้าง Excel
I2เซลล์ที่ล็อกออกมาตรงค่าที่ล็อกคีย์ normalize ที่ประตูเข้า · ล็อกเกินเป้าตอบ 400
I3หีบเป็นจำนวนเต็ม ไม่ติดลบปัดเป็น int ครั้งเดียวที่ประตูเข้า
I4force_min_one → ทุกคนได้ ≥ 1 หีบ (เมื่อเป้า ≥ จำนวนคน)รอดผ่านทั้ง proportional → LP → greedy
I5เซลล์อยู่ในรั้ว % จาก baselineข้อจำกัดใน LP + ขอบเขตใน greedy
I6SKU รหัสเดียวถูกกระจายรอบเดียวยุบซ้ำก่อนแบ่งกลุ่มตามแบรนด์
I7โหมดรวมภาคไม่ปน ตัวตน ข้ามทีมคีย์ล็อกมีรหัสซุปนำหน้า · ห้าม fallback ไปรหัสผู้จัดการ

6 · แก้มือและการเกลี่ยอัตโนมัติ

คลิกตัวเลขในตารางแล้วพิมพ์ใหม่ → ช่องนั้นกลายเป็น ล็อก ระบบจะไม่ขยับอีก แม้กดคำนวณใหม่ (ส่งไปเป็น locked_edits)

แต่ผลรวมต่อ SKU ต้องคงเดิม ระบบจึงไป เกลี่ยจากคนที่ยังไม่ถูกแก้ โดยอัตโนมัติ (autoRebalance) น้ำหนักการเกลี่ยใช้ hist_avg ของแต่ละคน

แผง「ผลจากการแก้ล่าสุด」

ทุกครั้งที่แก้ จะมีแผงขึ้นใต้ตารางบอกว่าไปกระทบใครบ้าง:

ผลจากการแก้ล่าสุด                                  ✕
  111294  ฟลอเร่สบู่ขมิ้น 80 ก.
  [คุณแก้]         C431 สมชาย  +1
  [ระบบเกลี่ยจาก]  C439 ชานนท์ SL460  −1
  ⚠️ ดึงข้ามทีม: SL460

ทำงานโดยถ่ายภาพก่อนแก้แล้ว diff หลังเกลี่ยเสร็จ จึงจับได้ทุกเส้นทาง ไม่ต้องพึ่งตัวเกลี่ยรายงานเอง

7 · โหมดรวมภาค

ผู้จัดการ (หรือซุปที่มี peer ในภาคเดียวกัน) เปิดดูหลายทีมพร้อมกันในตารางเดียวได้ และกระจายหีบได้ทั้งภาค

สิ่งที่ตรึง กับ สิ่งที่ขยับได้ — ต่างกันตามจังหวะ

จังหวะขอบเขตที่ถูกตรึงเพราะอะไร
กดคำนวณ / คำนวณใหม่ต่อทีม แต่ละซุปยิง /optimize แยก ใช้เป้าของตัวเอง + ประตู 409 บังคับ
แก้มือแล้วระบบเกลี่ยต่อทั้งภาค autoRebalance จัดกลุ่มด้วย sku ล้วน เทียบกับผลรวมเป้าทั้งภาค

ผลคือหลังแก้มือ ผลรวม SKU ทั้งภาค ยังตรง แต่สัดส่วน รายทีม เลื่อนจากเป้า TGA ของทีมนั้นได้ — เป็นพฤติกรรมที่ตั้งใจ

แถวรวมทีม — จุดเดียวที่มองเห็นการเลื่อน

ท้ายกลุ่มของแต่ละซุปมีแถบสรุปบอกยอดต่อ SKU และส่วนต่างจากเป้าของทีมนั้น

  • +3 สีส้ม = ทีมนี้ได้เกินเป้าตัวเอง 3 หีบ
  • −3 สีน้ำเงิน = ได้น้อยกว่าเป้าตัวเอง 3 หีบ
  • 「ตรงเป้าทีมทุก SKU」 = ยังไม่มีการย้ายข้ามทีม

เป้ารายทีมอ่านจาก target_boxes_by_sup ใน payload รวมภาค ไม่ใช่ยอดบวกรวมทั้งภาค

ตารางรวมภาคไม่ได้มาจากการกระจายสดเสมอไป

ตอนเปิดหน้ามา ระบบประกอบตารางจากสองแหล่งต่อทีม:

  • ทีมที่เคยกระจาย → snapshot เก่า ที่บันทึกไว้ตอนนั้น
  • ทีมที่ยังไม่เคยกระจาย → ตัวเลขจาก Target Sun ตรง ๆ

แถวรวมทีมจึงแสดงป้ายต่างกันตามแหล่ง — ทีมที่มาจาก Target Sun จะขึ้นว่า「ยังไม่ได้กระจาย」และไม่แสดง +/− เพราะเทียบกันไม่ได้

อื่น ๆ ที่ต่างจากมุมมองทีมเดียว

  • โหลดขนานกัน — ThreadPoolExecutor 6 thread (เพดาน 8) ปรับด้วย AGGREGATE_LOAD_WORKERS
  • ทีมพังทีมเดียวไม่ล้มทั้งภาค — เก็บ error รายทีม รายงานว่าทีมไหนพลาด ทีมที่สำเร็จบันทึกแล้ว
  • คำเตือน fallback รวมทุกทีม — ถ้าทีมใดตกไปใช้ proportional จะเตือนพร้อมระบุชื่อทีม
  • คีย์ล็อกมีรหัสซุปนำหน้า (SL330::E001) เพราะ emp_id ซ้ำข้ามทีมได้

ข้อสมมติที่ทั้งระบบแบกอยู่: uvicorn 1 worker เท่านั้น

route handler ทุกตัวเป็น def ไม่ใช่ async def → FastAPI โยนเข้า anyio threadpool (40 threads) → request หลายคนรันขนานกันจริงในโปรเซสเดียว ระบบจึงใช้ threading.Lock ป้องกัน

เพิ่มเป็น 2 worker หรือขึ้นหลาย container เมื่อไหร่ lock ทุกตัวไร้ผลทันที เพราะเป็น lock ระดับโปรเซส ต้องเปลี่ยนไปใช้ file lock หรือฐานข้อมูลก่อน — ไม่ใช่แค่เพิ่มตัวเลข worker

การบันทึกผลกระจาย — optimistic concurrency

client โหลด → เห็น version: 3
client บันทึก → ส่ง if_match_version: 3
   server: version บนดิสก์ == 3?  → เขียน version: 4 → 200
                          != 3?  → 409 พร้อมบอก version ปัจจุบัน

ใช้ version เป็นเลขจำนวนเต็ม ไม่ใช่ updated_at เพราะ autosave debounce 800ms ทำให้สอง save ในวินาทีเดียวกันได้ timestamp เท่ากัน = precondition มีรูให้เล็ดลอด

# ทั้งหมด (161 เทสต์)
python run_tests.py

# กฎคงที่ของการกระจาย — ในหน่วยความจำล้วน ไม่แตะไฟล์/เน็ต/DB
python -m pytest tests/test_or_engine_invariants.py -q

# ก่อน/หลังแก้อะไรที่อาจทำให้ตัวเลขขยับ
python scripts/golden_allocation.py capture
python scripts/golden_allocation.py compare -v

สิ่งที่ต้องรู้เกี่ยวกับ golden harness

  • CBC ไม่ deterministic 100% — มี time limit สูงสุด 60 วินาทีต่อการแก้หนึ่งครั้ง ทีมที่ SKU เยอะพอจะชน limit จะได้คำตอบ "ดีที่สุดเท่าที่หาทัน" รันซ้ำอาจต่าง 1–2 เคส
  • data/ เป็น cache ที่แอปเขียนทับได้ตลอด เป้าจึงเปลี่ยนโดยไม่มีใครแก้โค้ด harness เก็บลายนิ้วมือข้อมูลเข้าไว้ ถ้าต่างจะรายงานเป็น [ข้อมูลต้นทางเปลี่ยน] แยกออกมา
  • sku_mismatches ต้องเป็น 0 เสมอ ไม่ว่ากรณีไหน — ถ้าไม่ใช่คือกฎ I1 พัง

run_tests.py ถ่าย snapshot ไฟล์ config สำคัญก่อนรัน ถ้าเทสต์ไปแก้ไฟล์จริงจะ กู้คืนอัตโนมัติ + เตือน + exit 1 (เคยพบว่า config/app_runtime.json ถูกเปลี่ยน preset ปลายทาง Target Sun ระหว่างรันเทสต์)
