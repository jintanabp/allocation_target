## P0 — กติกาบังคับคลัง × คนแยกคลัง: หน้าเว็บตัดหีบของคลังที่ถูกบังคับทิ้งตอนประกอบข้อมูลส่ง

**พบ:** 22 ต.ค. 2026 ระหว่างลองข้อความ Q6 บนทีมทดสอบ SLDEMO4 (มีอยู่ก่อนแล้ว ไม่ได้เกิดจากการแก้วันนั้น)

**อาการ**
- พนักงานแยกคลัง (wh_split เช่น D408 = W1 / W2 / คลังว่าง) + กติกาบังคับ SKU ไปคลังที่เขา **ไม่มี** (เช่น W9)
- ขั้นที่ 3 (`optimize._apply_wh_pin_preview` ทาง ≥2 แถว) สร้างแถวใหม่ `D408|W9` ที่ได้หีบทั้งก้อน + ตั้งแถวคลังเดิมเป็น 0
  → บนจอยอด SKU ตรงเป้า
- ตอนกดส่ง `_lakehouseAllocationsFromStep3` วนตาม **แถวพนักงาน** (W1/W2/ว่าง) แล้วหาแถวผลด้วยคีย์ (คน, คลัง)
  → แถว W9 ไม่มีใครหยิบ หีบหาย (ทดสอบ: Q305 ส่ง 28 / เป้า 30)
- ด่าน `_confirmTargetMismatchBeforeSend` ขึ้น「ยอดหีบไม่ตรงเป้า — ยังไม่ได้ส่ง」ทั้งที่จอบอกว่าตรง → **ส่งทีมนั้นไม่ได้** (ไม่มีข้อมูลผิดเข้า Target Sun)
- กรณีคลังที่บังคับเป็นคลังที่คนนั้นมีอยู่แล้ว (`already_pinned`) ไม่เจอปัญหา เพราะมีแถวพนักงานของคลังนั้น

**ทางแก้ที่เสนอ (ต้องตัดสิน)**
- (ก) **แนะนำ** — ใน `_lakehouseAllocationsFromStep3` ปล่อยแถวผลที่ยังไม่ถูกหยิบ (หีบ > 0) ของพนักงานในขอบเขตออกไปด้วย
  เพิ่มเติมจากลูปเดิม (ใช้ชุด `emitted` เดิมกันซ้ำ) — server จัดการคลังตามกติกาเองอยู่แล้ว (`_apply_warehouse_pin_rules`)
  และ `_expand_allocations_with_tga_grain` ลงหีบของคลังที่ grain ไม่มีไปแถวที่ไม่มีใครระบุ → ยอดรวมเท่าเดิม
- (ข) ขั้นที่ 3 ไม่สร้างแถวคลังใหม่ให้คนแยกคลัง (ปล่อยหีบไว้ที่แถวเดิม แค่ติดป้าย 🔒 แบบคนคลังว่าง) — เปลี่ยนสิ่งที่ผู้ใช้เห็น
  ซึ่งเคยขอไว้ (22 ก.ย. 2026「บังคับจริงตั้งแต่ตอนกระจาย」) จึงไม่แนะนำ

**ตรวจหลังแก้**
- เทส JS: แถว `D408|W9` ต้องอยู่ใน payload ไม่ซ้ำ · คนไม่แยกคลังผลเหมือนเดิม
- ทีมทดสอบ SLDEMO4 (กติกา Q305 → W9): ด่านตรวจตอนกดส่งต้องไม่ขึ้น · `_build_tga_upload_dataframe(enforce_targets=True)`
  ด้วย payload จากหน้าเว็บจริง (ไม่ใช่ผล /optimize ตรง ๆ แบบที่เคยลอง) ต้องผ่าน ยอดต่อ SKU = เป้า และแถวคลังเดิมได้ 0
- เช็คบน server จริง: มีกติกาไหนที่บังคับไปคลังที่คนแยกคลังไม่มีบ้าง (อ่าน `data/warehouse_pin_rules.json` + `data/tga_lines_*`)
  — ถ้ามี = ผู้ใช้งวดนี้กำลังเจอ ต้องรีบ

## L12 — รหัส SKU เก่าที่ผูกแล้ว ถูกนับเป็น「สินค้าใหม่」และแบ่งเท่ากัน

**อาการ:** เมื่อรหัสเก่าและรหัสใหม่ที่ผูกกันไว้ (`sku_links`) มีเป้าในงวดเดียวกันทั้งคู่ ประวัติขายของรหัสเก่าถูกนับรวมไปที่รหัสใหม่
รหัสเก่าเองจึงดูเหมือน「ไม่เคยขาย」→ ขึ้นเตือน `new_sku_maybe_recoded` และถูกแบ่งเท่าทุกคน

**จุดในโค้ด**
- `backend/core/allocation_checks.py::detect_new_product_skus` — ไม่รู้จักการผูกรหัส
- `backend/services/employees.py::maybe_recoded_sku_warning` — ข้ามเฉพาะรหัสหลัก (`linked_canon_skus`) ไม่ข้ามรหัสเก่า
- `backend/services/optimize.py` ~บรรทัด 1742 (`new_product_skus_used` → `even_new_products`)

**ต้องตัดสิน:** รหัสเก่าที่ยังมีเป้าควรกระจายตามประวัติของใคร
- (ก) **แนะนำ** — ใช้ประวัติชุดเดียวกับรหัสใหม่ (กลุ่มที่ผูกกัน) และไม่นับเป็นสินค้าใหม่ / ไม่เตือนให้ผูกรหัส
- (ข) ใช้ประวัติของรหัสเก่าเองก่อนรวม

**ตรวจ:** เทส: SKU ที่อยู่ในกลุ่มผูกรหัส (ฝั่งเก่าหรือใหม่) ไม่อยู่ใน `detect_new_product_skus` และไม่ขึ้นคำเตือน ·
golden compare: เคสที่ขยับต้องเป็นเฉพาะ SKU ที่ผูกรหัส
