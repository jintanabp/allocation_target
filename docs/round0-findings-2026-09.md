# ผลตรวจรอบ 0 — สิ่งที่บันทึกการใช้งานบอก (4 ก.ย. 2026)

> รอบ 0 ของ [แผนแก้ตามผลสำรวจ](survey-plan-2026-09.md) คือ "วัดก่อนแก้"
> เอกสารนี้คือผลของครึ่งแรก ซึ่งอ่านจากบันทึกการใช้งานล้วน ๆ ยังไม่มีการแก้โค้ดใด ๆ
> ที่กระทบตัวเลขของผู้ใช้

**ขอบเขตข้อมูล:** บันทึกการใช้งาน 20 ก.ค. – 4 ก.ย. 2026 · 1,857 รายการ ·
ดาวน์โหลดจากแท็บ「บันทึกการใช้งาน」ในหน้าแอดมิน

---

## สรุปสำหรับผู้บริหาร

1. **คนที่บอกว่า "ส่งไม่สำเร็จ" กับคนที่ระบบบันทึกว่าส่งไม่สำเร็จ เป็นคนละกลุ่มกันเกือบทั้งหมด**
   — แปลว่าเราไม่เคยเห็นปัญหาที่ผู้ใช้เจอจริง
2. **มีการส่งที่สำเร็จแต่ยอดลงปลายทางไม่ตรงกับไฟล์ที่ส่ง 10 ครั้ง ใน 6 ทีม**
   ระบบติดธงไว้แล้วแต่ข้อความเขียนว่า "สำเร็จ" จึงไม่มีใครสังเกต
3. **คำเตือน "หน้าเว็บเวอร์ชันเก่า" 685 ครั้ง เป็นการเตือนที่ผิด** — แก้ข้อความแล้ว
4. **เป้าเปลี่ยนหลังทีมเริ่มทำงานไปแล้ว 178 ครั้ง ใน 47 ทีม** มากสุด +64,037 หีบ
   น่าจะเป็นส่วนสำคัญของเสียงร้องเรียนอันดับ 1 ("เป้าไม่ตรงหน้างาน" 29 เสียง)

---

## 1. สามทีมที่รายงานว่าส่งไม่สำเร็จ — ไม่มีทีมไหนส่งไม่สำเร็จจริง

| ทีม | สิ่งที่พบในบันทึก |
|---|---|
| SL531 | **ไม่มีบันทึกการกดส่งเลยสักครั้ง** แต่มีกิจกรรมอื่น 32 รายการ (บันทึกผลกระจาย 26 ครั้ง) |
| SL527 | **ไม่มีบันทึกการกดส่งเลยสักครั้ง** แต่มีกิจกรรมอื่น 81 รายการ |
| SL460 | กดส่ง 1 ครั้ง ระบบติดธงว่าผิดปกติ แต่ข้อความคือ "ส่งเข้า Target Sun **สำเร็จ**" |

ทั้งสามทีมใช้ระบบจริงและกระจายเป้าจริง แต่สองทีมไม่เคยไปถึงขั้นกดส่ง

**ทำไมถึงมองไม่เห็น:** ขั้น "เตรียมส่ง" ซึ่งเป็นด่านที่ระบบตีกลับได้ (เช่นข้อมูลไม่ครบ
หรือไม่มีสิทธิ์) **ไม่ถูกบันทึกเลย** ผู้ใช้ที่ติดตรงนั้นจึงหายไปจากบันทึกโดยไม่มีร่องรอย
— เป็นงานที่อยู่ในแผนรอบ B อยู่แล้ว และผลตรวจนี้ยืนยันว่าควรเลื่อนความสำคัญขึ้น

**ที่ส่งไม่สำเร็จจริงมี 4 ครั้ง จาก 4 ทีม** — SL453 · SL417 · SL382 · SL456
ทั้งหมดเป็นกรณีระบบปลายทางตอบกลับผิดพลาด (502) และ **ไม่มีทีมใดอยู่ในรายชื่อที่ร้องเรียน**

> ข้อนี้ยืนยันความไม่ตรงกันที่แผนตั้งข้อสังเกตไว้: แบบสอบถามได้ 7 เสียงว่าส่งไม่สำเร็จ
> ขณะที่ระบบจับได้ 3 ราย — แปลว่ามีคนติดปัญหาแล้วแก้เองได้โดยเราไม่เคยรู้

---

## 2. ส่งสำเร็จแต่ยอดลงไม่ตรง — 10 ครั้ง ใน 6 ทีม

ตัวอย่างจากบันทึกจริง:

```
งวด 2026-09 · ส่ง 1,158 แถว · เพิ่ม 0 · แก้ 1,158 · ข้าม 0
              ⚠ ยอดลงจริงไม่ตรงไฟล์ 102 SKU (+1,982 หีบ)
```

พบใน **SL307 · SL399 · SL453 · SL460 · SL514 · SL535** คิดเป็น 4% ของการส่งทั้งหมด (10 จาก 234)

ระบบตรวจเจอและติดธงระดับ "ผิดพลาด" ไว้แล้ว แต่**ข้อความที่แสดงคือ "ส่งเข้า Target Sun สำเร็จ"**
ทำให้ไม่มีใครสังเกต · นี่คือคำอธิบายว่าทำไม SL460 ถึงรายงานว่าส่งไม่สำเร็จ ทั้งที่ระบบบอกว่าสำเร็จ

**ต้องตัดสินใจ:** ยอดที่ไม่ตรงนี้เป็นเรื่องปกติของปลายทาง (เช่นมีการปัดหรือรวมยอด)
หรือเป็นข้อมูลผิดที่ต้องแก้ — ต้องถามเจ้าของระบบ Target Sun ก่อน

## 3. คำเตือน "หน้าเว็บเวอร์ชันเก่า" 685 ครั้ง — เป็นการเตือนที่ผิด

ระบบมีด่านกันไม่ให้คนสองคนบันทึกทับกัน โดยให้หน้าเว็บส่ง "เลขเวอร์ชัน" มาด้วยทุกครั้ง
ถ้าไม่ส่งมา ระบบจะบันทึกเตือนว่า *"บันทึกทับโดยไม่ส่ง version (client เก่า)"*

ตรวจแล้วพบว่า**ไม่ใช่หน้าเว็บเก่า** หลักฐานสองชิ้น:

- **29 จาก 41 คน** มีทั้งการบันทึกที่ส่งเวอร์ชันและไม่ส่งเวอร์ชัน — คนคนเดียวใช้หน้าเว็บ
  สองเวอร์ชันพร้อมกันไม่ได้
- **86% ของรายการ** เกิดในนาทีที่ผู้ใช้คนเดียวบันทึกให้หลายทีมพร้อมกัน = การกระจายทั้งภาค
  ซึ่ง **ออกแบบไว้ให้ตั้งใจทับทุกทีมอยู่แล้ว** จึงไม่ส่งเวอร์ชันโดยเจตนา

**ผลเสียที่ซ่อนอยู่:** ระบบตั้งใจใช้ตัวเลขนี้เป็นสัญญาณว่า "เมื่อไม่มีคำเตือนแล้ว = เปิดบังคับ
ด่านกันเขียนทับได้" แต่เส้นทางกระจายทั้งภาคจะสร้างคำเตือนนี้ตลอดไป ตัวเลขจึงไม่มีวันเป็นศูนย์
และไม่มีใครกล้าเปิดบังคับ — **ด่านกันเขียนทับจึงค้างอยู่ในสถานะไม่บังคับใช้มาตลอด**

**แก้แล้ว:** ให้หน้าเว็บบอกเหตุผลมาด้วยว่าทำไมไม่ส่งเวอร์ชัน แล้วแยกเป็นสามกรณี —
กระจายทั้งภาค (ปกติ ไม่ใช่คำเตือน) · ยังไม่ได้โหลดข้อมูลของงวดนั้น (ควรเฝ้า) ·
หน้าเว็บเก่าจริง (ต้องแก้) · หลังจากนี้ตัวเลขจะสะท้อนของจริง และตัดสินใจเปิดบังคับได้

## 4. เป้าเปลี่ยนหลังทีมเริ่มทำงาน — 178 ครั้ง ใน 47 ทีม

ระบบบันทึกไว้ทุกครั้งที่เป้าของงวดต่างจากตอนทีมเปิดงวดครั้งแรก

| | |
|---|---|
| จำนวนครั้ง | 178 |
| จำนวนทีมที่เจอ | 47 |
| ส่วนต่างมากสุด | **+64,037 หีบ** |
| ตัวอย่าง | SL531 เห็นเป้าเพิ่ม +20,880 หีบ เมื่อ 1 ก.ย. |

ทีมที่เกลี่ยเป้าเสร็จแล้วต้องกลับมาทำใหม่ทั้งหมดเมื่อเป้าเปลี่ยน · เชื่อมโดยตรงกับเสียง
ร้องเรียนอันดับ 1 ในแบบสอบถาม ("เป้าที่ระบบให้ไม่ตรงกับหน้างาน" 29 เสียง · 57%)

**ต้องตัดสินใจเชิงกระบวนการ ไม่ใช่เชิงระบบ:** เป้าควรถูกล็อกเมื่อไหร่ และใครมีสิทธิ์เปลี่ยน
หลังจากนั้น — ตรงกับคำถามที่ค้างอยู่เรื่องเจ้าของเป้าระหว่างทีมขายกับมาร์เก็ตติ้ง

## 5. เรื่องจำนวนบรรทัดที่ส่งเข้าระบบปลายทาง (SL396 / SL506)

ทั้งสองทีมร้องเรียนว่าช่องเป้าและบรรทัดมีมากเกินจำเป็น

| | |
|---|---|
| จำนวนครั้งที่ส่ง | ทีมละ 6 ครั้ง |
| แถวต่อครั้ง | **3,560 แถว** |
| แถวที่ระบบข้ามให้ | **0 ทุกครั้ง** |
| ครั้งแรกสร้างแถวใหม่ที่ปลายทาง | 1,234 แถว |

**ยังตอบไม่ได้ว่าการตัดแถวที่ไม่มีเป้าออกจะช่วยได้แค่ไหน** เพราะบันทึกไม่ได้เก็บว่าในจำนวน
ที่ส่งไปนั้นเป็นแถวที่ไม่มีเป้ากี่แถว — แผนสมมติว่ามีข้อมูลนี้ แต่จริง ๆ ไม่มี
ต้องรอวิเคราะห์จากไฟล์ผลกระจายแทน (ดูหัวข้อถัดไป)

## สิ่งที่ยังตอบไม่ได้ และกำลังทำอะไรอยู่

ตัวชี้วัดหลักของรอบ 0 คือ **"ซุปต้องแก้ตัวเลขที่ระบบให้มามากแค่ไหน"** ซึ่งเป็นตัวแบ่งกลุ่ม
ผู้ใช้ที่พอใจกับไม่พอใจในแบบสอบถาม — **ยังวัดไม่ได้** เพราะระบบไม่เคยเก็บว่าเครื่องคำนวณ
ให้เลขอะไรไว้ตั้งแต่แรก เก็บแต่เลขสุดท้ายหลังซุปแก้แล้ว

แก้ไปแล้วสองอย่าง (ทั้งคู่ไม่กระทบตัวเลขที่ผู้ใช้เห็นและไม่กระทบสิ่งที่ส่งออก):

1. **เริ่มเก็บเลขที่เครื่องคำนวณให้** ตั้งแต่งวดที่กระจายครั้งถัดไป
   ของแถมคือปุ่ม "คืนค่าที่ระบบกระจายให้" จะใช้งานได้จริงหลังรีเฟรช ซึ่งเป็นสิ่งที่มีผู้ใช้ขอมา
2. **เพิ่มปุ่มดาวน์โหลดผลกระจายทั้งงวด** ในหน้าแอดมิน เพื่อเอาข้อมูลออกมาวิเคราะห์ได้
   โดยไม่ต้องเข้าไปรันอะไรบนเซิร์ฟเวอร์
