# สถานะผลกระจาย (allocation status)

สถานะที่ manager/แอดมินเห็นในตาราง「สรุปผลกระจายรายทีม」มี 4 แบบ

| สถานะ | หมายถึง | ตั้งเมื่อไหร่ |
|---|---|---|
| **ยังไม่กระจาย** | ยังไม่มีผลกระจายบันทึกบน server | ไม่มี snapshot |
| **กระจายแล้ว** (`optimized`) | กดกระจายแล้ว **ยังไม่ได้แก้ตัวเลขเอง** | บันทึกตอนไม่มีแถวไหนมี `is_edited` |
| **แบบร่าง** (`draft`) | กระจายแล้วและ **แก้ตัวเลขด้วยมือ** ยังไม่ได้ส่ง | บันทึกตอนมีอย่างน้อย 1 แถวที่ `is_edited` |
| **ส่ง Target Sun แล้ว** (`sent_targetsun`) | ส่งเข้า Target Sun เรียบร้อย | ตอน `POST /lakehouse/import-targetsun` สำเร็จ |

## กฎที่ต้องรักษาไว้

**1. สถานะตัดสินจาก `is_edited` ไม่ใช่จาก call site**

`frontend/app.js: _deriveAllocStatus()` เป็นแหล่งเดียวที่ตัดสิน — `is_edited` ถูกตั้งเฉพาะตอน
ผู้ใช้แก้ตัวเลขจริง (`app.js:5952` และเช็คค่าซ้ำที่ `:5936` เพื่อไม่ให้แค่คลิกแล้ว blur นับเป็นการแก้)
และถูกล้างทุกครั้งที่กระจายใหม่ (`:5148`)

> ⚠️ **ห้ามฮาร์ดโค้ด `queueServerAllocationSave("draft")`** — นี่คือบั๊กเดิม: `saveDraft()` ถูกเรียก
> ตอน **"โหลดแบบร่าง"** (`app.js:8293`) ด้วย ทำให้แค่ super เปิดหน้าเว็บกลับมา สถานะบน server
> ก็ร่วงจาก `optimized` → `draft` ทั้งที่ไม่ได้แตะอะไร แล้ว manager เห็นเป็น「แบบร่าง」

**2. "ส่งแล้ว" คือบันทึก ไม่ใช่การล็อก**

เป้าอาจเปลี่ยนหรือเพิ่มในวันถัดไป — super ต้อง **กระจายใหม่หรือแก้แล้วส่งซ้ำได้เสมอ**
หน้าจอจึงไม่ถูกล็อกหลังส่ง (เดิม `app.js:8154` เคยตั้ง `readOnly` ตอนสถานะเป็น sent — ถอดออกแล้ว)

พอแก้ต่อหลังส่ง สถานะจะกลับเป็น **แบบร่าง** ตามกฎข้อ 1 แต่ **`target_sun_sent_at` ยังอยู่** →
ตารางสรุปจะขึ้น「แบบร่าง **(เคยส่งแล้ว)**」พร้อม tooltip บอกเวลาที่ส่งครั้งล่าสุด

`target_sun_sent_at` ถูกรักษาไว้ **ฝั่ง server** (`allocation_store.write_snapshot`) ไม่พึ่ง client
ส่งกลับมา — ไม่งั้น client เก่าที่ไม่รู้จัก field นี้จะลบประวัติทิ้ง

**3. โหมดรวมภาค — snapshot ต้องลงทีมเจ้าของจริงเท่านั้น**

`saveRegionalAllocationSnapshots()` แยกแถวตาม `supervisor_code` แล้วบันทึกทีละทีม
แถวที่ระบุทีมไม่ได้ **ต้องไม่ถูกบันทึก** และต้องเตือนผู้ใช้

> ⚠️ **ห้ามให้ `_supervisorCodeForAllocRow()` fallback ไป `S.supId` ในโหมดรวมภาค** —
> `S.supId` ตอนนั้นคือ **รหัสของผู้จัดการ** ไม่ใช่ทีมของแถวนั้น เดิม
> `_mergeLockedEditsIntoAllocs()` push แถวใหม่โดยไม่ใส่ `supervisor_code`
> แถวนั้นจึงไปโผล่ใน snapshot ของผู้จัดการแทนทีมจริง
>
> ด้วยเหตุผลเดียวกัน คีย์จับคู่ล็อกในโหมดรวมภาคต้องมีรหัสซุปนำหน้า (`SL330::E001`)
> เพราะ `emp_id` ซ้ำข้ามทีมได้ — ไม่งั้นล็อกของทีมหนึ่งจะไปตกกับคนของอีกทีม
> (ดู `_lockIdentityKey()` และ `docs/ALLOCATION_INVARIANTS.md` ข้อ I7)

**4. snapshot ไม่ถูกลบหลังส่ง**

เดิม `_markAllocationSentTargetSun` เรียก `deleteServerAllocationSnapshot` ทำให้
สถานะ `sent_targetsun` **ไปไม่ถึงเลยตั้งแต่วันแรก** (ใส่มาพร้อมกันใน commit `b860324`)
และไม่เหลือหลักฐานว่าทีมไหนส่งแล้ว ตอนนี้บันทึกสถานะแทนการลบ

## ตรวจว่าใครส่ง Target Sun ไปแล้วบ้าง

**สองที่ ใช้คนละงาน:**

| ที่ | ตอบอะไรได้ | ข้อจำกัด |
|---|---|---|
| ตาราง「สรุปผลกระจายรายทีม」 | สถานะ**ปัจจุบัน**ของแต่ละทีมในงวดนี้ | เห็นแค่ครั้งล่าสุดต่อ (ทีม × งวด) |
| หน้าแอดมิน →「บันทึกการใช้งาน」 | **ทุกครั้ง**ที่มีคนกดส่ง ใคร ทีมไหน เมื่อไหร่ กี่แถว สำเร็จหรือไม่ | — |

log ใช้ `action = "send_targetsun"` (`backend/routers/lakehouse.py: _log_targetsun_send`)
บันทึกทั้งตอนสำเร็จ (`level=info`) และล้มเหลว (`level=error`) เก็บที่ `data/logs/usage_{วันที่}.jsonl`

> **log เป็น append-only — ไม่มีการลบ** ฟังก์ชัน `acknowledge_logs` กับปุ่ม「รับทราบแล้ว」
> ที่เคยลบรายการทิ้งถูกถอดออกแล้ว เพราะทำให้ตาม monitor ย้อนหลังไม่ได้
> ถ้าไฟล์ใหญ่เกินในอนาคต ให้ทำ rotate/archive ตามวันที่ **อย่ากลับไปลบรายรายการ**

การส่งยังเขียน technical log ที่ `data/app.log` ด้วย (`services/targetsun_import.py`)
แต่นั่นไว้ debug ไม่ใช่ audit
