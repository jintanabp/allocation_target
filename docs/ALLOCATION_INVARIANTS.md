# กฎคงที่ของการกระจายหีบ (Allocation Invariants)

เอกสารนี้คือ **สัญญาของเครื่องกระจายหีบ** — สิ่งที่ต้องจริงเสมอไม่ว่าจะเลือกกลยุทธ์ไหน
ติ๊กตัวเลือกอะไร หรือล็อกกี่เซลล์

อ่านก่อนแตะ `backend/OR_engine.py` หรือ `backend/services/optimize.py`
ถ้าจะแก้อะไรที่ทำให้ข้อใดข้อหนึ่งข้างล่างไม่จริง **นั่นคือบั๊ก ไม่ใช่ฟีเจอร์**

ที่มา: เอกสารนี้เกิดจากผลตรวจสอบที่พบว่ากฎเหล่านี้ถูกละเมิดได้จริงหลายทาง
โดยไม่มีอะไรจับได้เลย เพราะไม่เคยมีที่ไหนเขียนไว้ว่ากฎคืออะไร

---

## I1 — ผลรวมหีบต่อ SKU ต้องเท่ากับเป้าเป๊ะ

```
สำหรับทุก sku:  sum(allocated_boxes) == supervisor_target_boxes
```

ไม่มีข้อยกเว้น ไม่ปัดขึ้น ไม่ปัดลง ไม่ "ใกล้เคียงพอ"

ตรวจโดย `backend/core/allocation_checks.py::validate_allocation_vs_targets`
และ **บังคับใช้จริง** ใน `run_optimization_service` — ถ้าไม่ผ่านจะตอบ HTTP 409
และ **ไม่เขียนไฟล์ผล ไม่สร้าง Excel**

> เดิมข้อนี้เป็นแค่ `logger.warning` ผลที่ผิดจึงถูกเขียนลงไฟล์ สร้าง Excel
> และตอบ 200 ตามปกติ ผู้ใช้ไม่มีทางรู้เลยว่าตัวเลขไม่ตรง

## I2 — เซลล์ที่ผู้ใช้ล็อกต้องออกมาตรงค่าที่ล็อก

```
สำหรับทุก (emp, sku) ใน locked_edits:  allocated_boxes == locked_boxes
```

การล็อกคือเจตนาที่ชัดเจนของหัวหน้า ห้ามตัวปรับสมดุลหรือ LP ไปขยับ

**การจับคู่คีย์:** `emp_id` และ `sku` ถูก normalize (`.strip()`) ที่ประตูทางเข้าเครื่อง
คำนวณด้วย `_normalize_engine_inputs()` — ทุกฝั่งหลังจากนั้นเทียบคีย์ได้ตรง ๆ

> เดิม `locked_map` ใช้ string ดิบจาก request แต่ `even_skus` / `base_map` / `flex_skus`
> ใช้ `_norm_sku()` ต่างกันแค่ช่องว่างหน้า-หลังก็ทำให้ล็อกถูกเมินเงียบ ๆ

**ถ้าล็อกรวมเกินเป้า SKU:** ระบบปฏิเสธด้วย HTTP 400 พร้อมบอกชื่อ SKU
ไม่ใช่กลบส่วนเกินแล้วปล่อยผลที่เกินเป้าออกไป

## I3 — หีบเป็นจำนวนเต็มไม่ติดลบ

```
allocated_boxes ∈ ℤ  และ  allocated_boxes >= 0
```

`supervisor_target_boxes` ถูกปัดเป็น `int` ครั้งเดียวที่ `_normalize_engine_inputs()`
ทุกที่ที่ใช้ต่อจากนั้นต้องอ่านค่าที่ปัดแล้ว **ห้ามใช้ `int()` ปัดเองซ้ำ**
(`int()` ตัดทศนิยม แต่ `int(round())` ปัด — เป้า 10.7 จะกลายเป็น 10 กับ 11 คนละที่)

## I4 — force_min_one รับประกันขั้นต่ำ 1 หีบ

```
ถ้า force_min_one และ supervisor_target_boxes >= จำนวนพนักงาน:
    ทุกคนต้องได้ >= 1 หีบใน SKU นั้น
```

ต้องอยู่รอดผ่านทั้ง `_proportional` → `_lp_optimize` → `_greedy_revenue_balancer`
ตัวปรับสมดุลมี `floors` กันไม่ให้ดึงหีบจนต่ำกว่าขั้นต่ำ

## I5 — เซลล์ต้องอยู่ในรั้วจากประวัติ

```
ถ้า baseline(emp, sku) > 0:
    lo <= allocated_boxes <= hi     โดย [lo, hi] = baseline ± band
```

| ประเภท SKU | รั้ว | ค่าคงที่ |
|---|---|---|
| SKU หลัก (flex, ~80% ของมูลค่าเป้า) | ±35% | `_TIER_FLEX_BAND_PCT` |
| SKU รอง (strict) | ±12% | `_TIER_STRICT_BAND_PCT` |
| ไม่เปิดโหมดหลัก/รอง | ±20% | `_DEFAULT_HIST_BAND_PCT` |
| สินค้าใหม่ที่ติ๊กแบ่งเท่า | ไม่ใช้รั้ว — ล็อกตามค่าแบ่งเท่า | — |

**เซลล์ที่ baseline = 0** (คนที่ไม่เคยขาย SKU นั้น) — ใน LP ไม่มีขอบบนจากรั้ว %
เพราะไม่มี baseline ให้อ้างอิง มีเพดานสัมบูรณ์ `ceil(เป้า ÷ จำนวนคน × cap_multiplier)`
ให้เลือกเปิดได้ผ่าน `ALLOC_ZERO_BASELINE_CAP=1`

> **ค่าเริ่มต้นคือปิด** — วัดกับข้อมูลจริง 8 ทีมแล้วพบว่าเปิดแล้วหีบย้ายที่ราว
> **2–3.5% ของทั้งทีม** (ผลรวมต่อ SKU ยังตรงเป้าทุกกรณี แค่ย้ายจากคนที่ไม่มีประวัติ
> ไปหาคนที่มีประวัติ) ซึ่งหัวหน้าทีมจะเห็นตัวเลขเปลี่ยนทันที จึงถือเป็น
> **การตัดสินใจเชิงนโยบาย** ไม่ใช่บั๊กที่ต้องปิดทันที
>
> ตัวคุมชั้นแรกทำงานอยู่แล้วทั้งหมด: `_cap_and_redistribute` (เพดาน mean × cap),
> anchor term ที่ถ่วงด้วยราคา, และสมการผลรวมต่อ SKU
> เพดานนี้เป็นการทำให้เจตนาอยู่ในรูป "ข้อจำกัด" แทนที่จะเป็นผลข้างเคียงของ objective

## I6 — SKU หนึ่งรหัสถูกกระจายรอบเดียว

SKU ที่ปรากฏหลายแถวใน `target_boxes` (เช่นอยู่สองแบรนด์) ต้องถูกยุบเป็นแถวเดียว
ก่อนเข้าเครื่องคำนวณ

> เดิมใช้ `dict(zip(...))` ซึ่งเก็บแค่แถวสุดท้าย และในโหมดหลายกลยุทธ์
> ที่แบ่งกลุ่มตามแบรนด์ SKU เดียวกันจะไปอยู่สองกลุ่ม แล้วถูกกระจาย **ซ้ำสองรอบ**

## I8 — พนักงานที่ส่งเข้ามาต้องมีแถวกลับออกไปเสมอ (หีบ 0 ได้)

`validate_allocation_vs_targets` (I1) รวมยอด **ต่อ SKU อย่างเดียว ไม่มีแกนพนักงาน**
ถ้าพนักงานคนหนึ่งหลุดออกจากผลลัพธ์ หีบของเขาจะถูกเกลี่ยไปคนอื่นแล้วยอดต่อ SKU ยังตรงเป้า
→ ทุกด่านผ่าน ทั้งที่หีบไปตกผิดคน (พิสูจน์ด้วยการรันใน `tests/test_employee_conservation.py`)

"ไม่มีแถว" กับ "มีแถวแต่เป็น 0" ต่างกันมากสำหรับทุกอย่างปลายน้ำ: ตารางขั้นที่ 3 สร้างแถว
จากผลลัพธ์ ไม่มีแถว = ไม่มีคนคนนั้นบนจอ แล้วตัวเกลี่ยอัตโนมัติมองว่ายอดขาดและยกหีบไปให้เพื่อน

`missing_employee_alloc_keys` + `zero_fill_missing_employees` (`core/allocation_checks.py`)
ทำงานหลัง `restore_allocation_emp_ids` และ **ก่อน** ด่าน I1 เพื่อให้ I1 ตรวจกับ frame เดียว
กับที่เขียนไฟล์จริง · เติมเฉพาะแถวหีบ 0 จึงเปลี่ยนผลรวมต่อ SKU ไม่ได้เลย
เป้าเงิน 0 หายไป = ถูกต้องตามกติกา (log info) · เป้าเงิน > 0 หายไป = ท่อพัง (log error)

### เป้าตั้งต้นของงวด — หลักฐานกันเป้าหาย

`data/target_boxes_{SL}_{งวด}.csv` ถูก **เขียนทับ** ทุกครั้งที่โหลดขั้นที่ 1 ใหม่ และเดิม
ไม่มีสำเนาเก่าเก็บไว้เลย เป้าเปลี่ยน/หายแล้วไม่มีอะไรให้เทียบหรือกู้

`data/baselines/{SL}_{ปี}_{เดือน}.json` คือสำเนาชุดแรก **เขียนครั้งเดียวแล้วไม่แตะอีก**
(ถ้าเขียนทับเรื่อย ๆ ก็เป็นแค่สำเนาค่าล่าสุด = ไร้ประโยชน์) · อยู่ในโฟลเดอร์ย่อยจึงไม่ถูก
ตัวล้าง cache ตามอายุแตะ · รอบถัดไปที่เป้าต่างจากตั้งต้นจะเขียน log `target_baseline_drift`
พร้อมค่าก่อน/หลังราย SKU · `POST /admin/target-baseline/restore` เขียนกลับได้ **dev เท่านั้น**
(ทับข้อมูลที่ทีมอื่นอาจใช้อยู่) และไม่แตะ snapshot ผลกระจาย

### พนักงานที่ไม่ต้องตั้งเป้า — ข้อยกเว้นที่ตั้งใจ ไม่ใช่การละเมิด I8

รายชื่อใน `config/no_target_employees.json` ถูกตัดออกจากคำขอ **ก่อน** `_requested_alloc_keys`
จึงไม่เคยอยู่ในชุดที่ I8 เฝ้า — I8 ยังบังคับเต็มกับทุกคนที่เหลือ

ลำดับนี้พลิกไม่ได้: ถ้าถ่ายรูปชุดพนักงานก่อนแล้วค่อยตัด I8 จะทำงานถูกตามหน้าที่ตัวเอง
(เติมแถว 0 ให้คนที่หายไป) แล้วคนที่แอดมินกันไว้จะโผล่กลับมาในตารางขั้นที่ 3

ต่างจาก "ไม่นำไปกระจายเป้า" ที่ระบบอนุมานจากเป้าเงิน: ชุดนี้เป็น **การตัดสินใจของคน**
อยู่ถาวรจนกว่าจะปลด ไม่หายเมื่อเป้าต้นทางเปลี่ยน และไม่ถูกคำนวณกลับมาเองตอนรีเฟรชเป้าสด
(ฝั่งหน้าเว็บจึงต้องเคารพ `no_target` ทั้งใน `_isAllocEligible` **และ** `_enrichEmployeeAllocFlags`
ตัวหลังคำนวณ flag ใหม่จาก `target_sun` ล้วน แก้ตัวเดียวไม่พอ)

คีย์เป็น (รหัสซุป, รหัสพนักงาน) เพราะ `emp_id` ซ้ำข้ามทีมได้ (I7) — กัน SL509 ต้องไม่พลอยกัน SL397
`/optimize` อ่านทีมจาก `supervisor_code` ที่หน้าเว็บส่งมา ถ้าไม่มี (หน้าเว็บรุ่นเก่าค้างในเบราว์เซอร์)
จะตกไปใช้ชุดรวมของทุกทีมในคำขอนั้น — **กันเกินดีกว่ากันขาด** เพราะกันเกินเห็นทันทีบนจอและปลดได้
ส่วนกันขาดคือหีบไหลไปหาคนที่ไม่ควรได้แล้วถูกส่งขึ้นระบบจริง

**เป้าหีบของทีมไม่ลดตาม (I1)** — คนที่เหลือรับส่วนนั้นไป รายชื่อนี้ตัดแค่ "ใครรับได้" ไม่ได้ลดเป้า

## I9 — กติกา "หน่วยไม่เคยขาย = เป้า 0" ต้องคิดแผนก่อน `_proportional` เสมอ

```
ถ้าเปิดกติกา และ (emp, sku) ไม่เคยขายกันเลยใน 12 เดือนล่าสุด:
    allocated_boxes == 0     (เว้นแต่เข้าข้อยกเว้นด้านล่าง หรือ force_min_one บังคับ 1)
```

`_never_sold_plan()` (`backend/OR_engine.py:498`) **ต้องถูกเรียกก่อน `_proportional` เสมอ**
(เรียกที่ `allocate_boxes():293`) เพราะ baseline ที่ I5 ใช้กั้นรั้ว ±% มาจากผลของรอบ
`_proportional` — ถ้าใส่กติกานี้เฉพาะฝั่ง LP โดยไม่ให้ `_proportional` เห็นด้วย รั้วจะอ้างอิง
คนละชุดข้อมูลกับคำตอบที่ต้องการ แล้วโจทย์ LP จะแก้ไม่ได้ ตกไป fallback ทั้งทีมโดยไม่มีใครรู้สาเหตุ

**ผลลัพธ์ของ `_never_sold_plan()` ต้องถูกส่งต่อให้ครบทั้ง 4 จุด** (`zero_pairs=` ใน
`_proportional`, `_lp_optimize`, `_greedy_revenue_balancer`, และรวมเข้า `even_skus` สำหรับ
SKU ที่เข้าเงื่อนไขเฉลี่ย) — ขาดจุดใดจุดหนึ่งจะได้พฤติกรรมคนละแบบระหว่างรอบแรกกับรอบเกลี่ยเงิน

**ข้อยกเว้น 2 แบบ (เฉลี่ยให้ทุกคนแทนการตัดเป็น 0):**

1. **ทั้งทีมไม่มีใครเคยขาย SKU นั้นเลย** — ไม่มี baseline ให้ยึด บังคับเป็น 0 ทั้งทีมจะผิดสัดส่วนกว่า
2. **เป้าใหญ่เกิน `push_multiple` เท่า** (ค่าเริ่มต้น 5) ของประวัติรวมของคนที่เคยขาย — ป้องกัน
   สินค้าที่เพิ่งถูกดันเป้าไปกองที่คนเดียวเพราะเขาคือคนเดียวที่มีประวัติ

**ลำดับความสำคัญ: `force_min_one` ชนะกติกานี้เสมอ** — ถ้าผู้ใช้ติ๊ก "ทุกคนอย่างน้อย 1 หีบ"
คนที่ไม่เคยขายจะได้พอดี 1 หีบ ไม่ใช่ 0 (คำสั่งชัดเจนของผู้ใช้ชนะกติกาอัตโนมัติ)

**"ไม่มีข้อมูล" ≠ "ไม่เคยขาย"** — แคชประวัติ 12 เดือน (`hist_cache_{sup}_{ปี}_{เดือน}_12m.csv`)
ว่างทั้งไฟล์แปลว่ายังไม่เคยดึง ไม่ใช่ "ไม่มีใครเคยขายอะไรเลย" ตีความผิดจะตัดเป้าทั้งทีมในคลิกเดียว
กันไว้สองชั้น: `optimize.py` ปิดกติกาเองพร้อม log เมื่อไม่มีแคช (`never_sold_off_reason:
no_hist_12m`) และ `_never_sold_plan()` เองก็ไม่ทำงานถ้า `df_sold_12m` เป็น `None`/ว่าง

เปิด/ปิดทั้งระบบหรือรายทีมได้จากหน้าแอดมิน (`backend/services/alloc_rules_store.py`,
ไม่ต้อง deploy) — ตรวจว่ากติกายังทำงานถูกด้วย `tests/test_never_sold_zero.py`

## I7 — โหมดรวมภาคไม่ปน "ตัวตน" ข้ามทีม

- คีย์ล็อกในโหมดรวมภาคมีรหัสซุปนำหน้า (`SL330::E001`) เพราะ `emp_id` ซ้ำข้ามทีมได้
- ทุกแถวผลลัพธ์ต้องระบุ `supervisor_code` ของทีมเจ้าของจริง
- แถวที่ระบุทีมไม่ได้ **ห้ามบันทึก** — ห้าม fallback ไปใช้รหัสผู้จัดการ
- meta (เช่น "ตกไปใช้ proportional") ต้องรวมทุกทีม ไม่ใช่เอาของทีมสุดท้ายทับ

### แต่ "หีบ" ย้ายข้ามทีมได้ — โดยตั้งใจ

นี่เป็นข้อยกเว้นที่ตั้งใจ ไม่ใช่บั๊ก แยกให้ชัดว่าอะไรถูกตรึงตอนไหน:

ผู้ใช้เลือกขอบเขตเองทุกครั้งที่กดกระจาย — modal สองตัวเลือก (`openAllocScopeModal`)
ค่าเริ่มต้นคือ **แยกตามทีม** เสมอ และไม่จำข้ามงวด (`S.allocScope` ถูกรีเซ็ตใน `applyDataPayload`)

| จังหวะ | ขอบเขตที่ถูกตรึง |
|---|---|
| **กดคำนวณ · ขอบเขต「แยกตามทีม」** | **ต่อทีม** — แต่ละซุปยิง `/optimize` แยก ใช้เป้าของตัวเอง และมีประตู 409 บังคับ (I1) |
| **กดคำนวณ · ขอบเขต「รวมเป้าทั้งภาค」** | **ทั้งภาค** — ยิง `/optimize` ครั้งเดียว ส่ง `target_sup_ids` ครบทุกทีม server บวกเป้าหีบเป็นก้อนเดียว (`load_summed_target_boxes`) แล้ว I1 บังคับกับ **ยอดรวมภาค** |
| **แก้มือแล้วระบบเกลี่ยต่อ** | **ทั้งภาค** — `autoRebalance()` จัดกลุ่มด้วย `sku` ล้วน เทียบกับผลรวมเป้าทั้งภาค |

### โหมด「รวมเป้าทั้งภาค」— กติกาที่ห้ามพัง

- **ห้าม fallback ไปไฟล์เป้า global** ตอนบวกข้ามทีม: ถ้าหลายทีมตกไปอ่าน `data/target_boxes.csv`
  ไฟล์เดียวกัน ผลรวมจะกลายเป็นเป้าเดิม × จำนวนทีม แล้ว I1 จะ **บังคับให้กระจายหีบเกินจริง**
  ออกไปทั้งภาคโดยที่ทุกด่านมองว่า "ตรงเป้า" → `load_summed_target_boxes` จึงคืนรายชื่อทีมที่ไม่มีไฟล์
  ให้ผู้เรียกปฏิเสธด้วย 400
- **รหัสทีมซ้ำในลิสต์ต้องไม่บวกซ้ำ** และ SKU ซ้ำในไฟล์ของทีมเดียวต้องยุบก่อนบวก (I6)
- **ตรวจสิทธิ์ทุกรหัสใน `target_sup_ids`** ไม่ใช่แค่รหัสที่ยิง request — เป้าของทีมอื่นคือฐานคำนวณ
- ไม่มี "ทีมเจ้าของเป้า" อีกแล้ว รหัสที่ยิง request เหลือหน้าที่เป็นที่อยู่ของไฟล์ผล/Excel
  และฐานตรวจสินค้าใหม่เท่านั้น — Excel ใช้ไฟล์เป้ารวมแยกต่างหาก
  (`target_boxes_union_*`) จะได้ไม่โชว์เป้าทีมเดียวคู่กับหีบทั้งภาค

ผลคือหลังแก้มือ ผลรวม SKU **ทั้งภาค** ยังตรง แต่สัดส่วน **รายทีม** เลื่อนจากเป้า TGA ของทีมนั้นได้

**เพราะเลื่อนได้ หน้าจอจึงต้องบอก** — ตารางรวมภาคมี **แถวรวมรายทีม** ต่อท้ายกลุ่มของแต่ละซุป
แสดงยอดต่อ SKU พร้อมส่วนต่างจากเป้าของทีมนั้น (`+3` / `-3` และไฮไลต์สี)
ข้อมูลเป้ารายทีมมาจาก `target_boxes_by_sup` ใน payload รวมภาค (`merge_employees_payloads`)

> `PUT /data/allocations` **ไม่ตรวจ** ผลรวมต่อ SKU — snapshot ที่รายทีมเลื่อนจากเป้าตัวเอง
> จึงบันทึกได้ ซึ่งเป็นพฤติกรรมที่ต้องการในโหมดนี้
>
> การเลื่อนข้ามทีมจะถูกล้างเมื่อกดคำนวณใหม่ **ในขอบเขต「แยกตามทีม」** เพราะแต่ละซุป
> re-pin กับเป้าตัวเอง และล็อกถูกส่งเฉพาะซุปเจ้าของ — การแก้ +5 ใน SL330 จึงถูกชดเชย
> ด้วยคนใน SL330 ด้วยกัน ส่วนขอบเขต「รวมเป้าทั้งภาค」ไม่ล้าง เพราะเป้าที่ pin คือยอดรวมภาค

### ช่องที่ผู้ใช้ "คลิกแล้วไม่แก้เลข" = ล็อกไว้

`onResultEdit` ถือว่าการคลิกเข้าไปในช่องแล้วออกโดยตัวเลขไม่เปลี่ยน = **ล็อกค่านั้นไว้**
(`is_edited = true`) — ตัวเกลี่ยหยิบเฉพาะช่องที่ยังไม่ล็อก และรอบคำนวณใหม่ส่งค่านี้ไปเป็น
`locked_edits` เดิมถือว่า "ไม่ได้แก้" ผู้ใช้จึงไม่มีทางบอกระบบได้เลยว่าช่องไหนห้ามขยับ
แล้วเลขที่ตั้งใจคงไว้ถูกเกลี่ยหายตอนไปแก้ช่องอื่น · ปลดล็อกด้วยปุ่ม ↺ ที่ช่องนั้น

### ประตูสุดท้ายอยู่ที่ "ตอนส่ง" ไม่ใช่ตอนบันทึก

`_assert_send_matches_sup_targets()` ใน `lakehouse.py` ตรวจก่อนสร้าง payload ส่ง Target Sun:
ผลรวมหีบต่อ SKU **ของทีมนั้น** ต้องตรงเป้าใน `target_boxes_{SUP}_{งวด}.csv`

ไม่ตรง → **409 `send_target_mismatch`** พร้อมรายการ SKU (ส่งกลับสูงสุด 20 รายการ)

หน้าเว็บตรวจล่วงหน้าฝั่ง client (`_confirmTargetMismatchBeforeSend`) แล้วเปิด modal
ให้ดูรายทีม/ราย SKU ว่าต่างเท่าไร ถ้ากด **ยืนยันส่ง** จะส่งซ้ำด้วย
`confirm_target_mismatch: true` ซึ่ง server ยอมให้ผ่านและ log ไว้

| ชั้น | ตรวจอะไร | ผ่านได้ยังไง |
|---|---|---|
| `/optimize` | ผลรวมต่อ SKU ต่อทีมทันทีหลังกระจาย | ต้องตรงเสมอ (`ALLOC_ALLOW_MISMATCH` = ทางออกฉุกเฉิน) |
| `PUT /data/allocations` | ไม่ตรวจ | — |
| **ดาวน์โหลด Excel** | **ไม่ตรวจ — โดยตั้งใจ** | ต้องโหลดมาตรวจได้เสมอแม้ตัวเลขยังไม่ตรง (และไม่ตัด SKU ทิ้งด้วย) |
| ส่ง Target Sun | ผลรวมต่อ SKU ต่อทีม เทียบเป้าปัจจุบัน | ผู้ใช้กดยืนยันหลังเห็นรายการ |
| ส่ง Target Sun (ไฟล์สุดท้าย) | ยอดในไฟล์ต้องเท่าผลกระจาย | **ผ่านไม่ได้** — ต่างเมื่อไรคือระบบพัง |

> ⚠️ `_build_tga_upload_dataframe()` ถูกใช้ร่วมกันทั้งการ **สร้างไฟล์ให้ดาวน์โหลด** และ
> การ **ส่งจริง** ประตูจึงคุมด้วยพารามิเตอร์ `enforce_targets` (ค่าเริ่มต้น `False`)
> และเปิดเป็น `True` เฉพาะใน `targetsun_import.py` เท่านั้น
>
> **ห้ามย้ายการตรวจเข้าไปในตัวสร้างแบบไม่มีเงื่อนไข** — จะทำให้ดาวน์โหลด Excel มาตรวจไม่ได้
> เมื่อตัวเลขมีปัญหา ซึ่งกลับหัวกลับหางกับสิ่งที่ผู้ใช้ต้องการตอนนั้น
> (`tests/test_send_target_gate.py::TestGateWiring` เฝ้าเรื่องนี้อยู่)

**ทำไมต้องตรวจซ้ำตอนส่ง** — ระหว่างกระจายเสร็จกับกดส่ง มีหลายก้าวที่ไม่มีใครตรวจ:
แก้มือ (ย้ายข้ามทีมได้), บันทึก snapshot, หรือโหลด snapshot เก่ากลับมาส่งทั้งที่เป้า TGA
เปลี่ยนไปแล้ว ตัวเลขที่ถึง Target Sun จึงต่างจากเป้าได้ทั้งที่ตอนกระจายถูกต้อง

### ประตูฝั่งส่งมี 4 ด่านที่ยืนยันได้ + 3 ด่านที่ข้ามไม่ได้

| ด่าน | รหัส 409 | flag ยืนยัน | ความหมาย |
|---|---|---|---|
| 1 | `send_target_mismatch` | `confirm_target_mismatch` | ตรวจแล้วยอดไม่ตรงเป้าทีม (ปกติในโหมดรวมภาคตาม I7) |
| 2 | `send_target_shortfall` | `confirm_manual_topup` | มี SKU ที่ส่งไม่ครบ → **ตัด SKU นั้นทั้งตัว** |
| 3 | `send_target_unverifiable` | `confirm_unverifiable_target` | ไม่มีไฟล์เป้าให้ตรวจเลย |
| 4 | `send_target_stale` | `confirm_stale_target` | เป้าต้นทางขยับหลังโหลดขั้นที่ 1 |
| — | `send_file_total_changed` | **ไม่มี — ข้ามไม่ได้** | ยอดในไฟล์จริงไม่ตรงกับผลกระจาย |
| — | `send_batch_total_mismatch` | **ไม่มี — ข้ามไม่ได้** | ยอดรวมของทั้งชุดไม่เท่าเป้ารวม |
| — | `send_batch_sku_partial` | — (ระบบเตรียมใหม่เอง) | SKU ถูกตัดบางทีม แต่ทีมอื่นยังส่ง |

ลำดับจริงตอนกดส่ง: **เตรียมทุกทีม → ถามครบทุกด่าน → ตรวจยอดรวมทั้งชุด → ค่อยส่งทีมแรก**
(`POST /lakehouse/verify-send-batch` คั่นกลาง — `tests/test_send_order_frontend.py` ตรึงลำดับนี้ไว้)

**สาม flag ต้องแยกกันเสมอ** — "ตรวจแล้วไม่ตรงแต่ตั้งใจ" กับ "ตรวจไม่ได้เลย" เป็นความเสี่ยง
คนละแบบ ถ้าใช้ flag ร่วมกัน การกดยืนยันเรื่องหนึ่งจะปลดล็อกอีกเรื่องที่ผู้ใช้ไม่เคยเห็น
(ในโหมดรวมภาคผู้ใช้กดยืนยันด่าน 1 จนชิน ปัญหา master data จะถูกกดข้ามไปโดยไม่ได้อ่าน)

**นโยบายด่าน 2 — SKU ที่ส่งได้ไม่ครบ ต้องไม่ส่งทั้งตัว**
เหตุที่ส่งไม่ครบคือ Target Sun ไม่เคยมีแถวของคู่พนักงาน×สินค้านั้น จึงเขียนทับไม่ได้
ถ้าส่งเฉพาะส่วนที่ส่งได้ เป้าของ SKU นั้นจะกลายเป็นครึ่ง ๆ กลาง ๆ (บางคนถูกทับด้วยเลขใหม่
บางคนค้างเลขเก่า) ตัดทั้ง SKU แล้วของเดิมยังอยู่ครบ ผู้ใช้ไปเกลี่ยเองใน Target Sun ได้
ผลพลอยได้: **ทุก SKU ที่อยู่ในไฟล์ต้องตรงเป้าเป๊ะ ไม่มีข้อยกเว้น**

**ก่อนส่ง: เตือนเมื่อเป้าต้นทางขยับ** (`send_target_stale`, ยืนยันได้ด้วย `confirm_stale_target`)
`assert_target_snapshot_is_fresh()` อ่านเป้าปัจจุบันจาก Target Sun มาเทียบกับไฟล์เป้าที่
ดึงมาตอนขั้นที่ 1 หลักการเทียบยอดยังยึด snapshot เสมอ ตัวนี้เป็นการ "บอกให้รู้"
ว่าข้อมูลอ้างอิงเก่าไปแล้ว ไม่ใช่การตัดสินว่าไฟล์ผิด

> ⚠️ อยู่ใน **เส้นทางส่งเท่านั้น** (`targetsun_import.py`) ห้ามย้ายกลับเข้า
> `_build_tga_upload_dataframe` — ตัวสร้างไฟล์ต้องออฟไลน์ล้วน ไม่งั้นการดาวน์โหลด Excel
> และชุดเทสต์จะยิงเน็ตขึ้นระบบจริงโดยไม่มีใครตั้งใจ (เคยพลาดมาแล้ว มีเทสต์เฝ้าอยู่ที่
> `tests/test_send_readback_and_freshness.py::TestBuilderStaysOffline`)

**หลังส่ง: ตรวจว่ายอดลงจริงครบ** (`readback` ในคำตอบของ import)
`verify_after_send()` อ่านเป้าที่ Target Sun ถืออยู่หลังส่ง มาเทียบกับไฟล์ที่เพิ่งส่งไป
เป็นตาข่ายชั้นเดียวที่จับได้ว่าปลายทางข้ามหรือปฏิเสธบางแถวเงียบ ๆ ทั้งที่ตอบว่าสำเร็จ
รายงานอย่างเดียว ห้าม raise (ส่งไปแล้วย้อนไม่ได้ ถ้าตรวจไม่ได้ก็แค่บอกว่าตรวจไม่ได้)
ผลถูกบันทึกลง audit log และเด้ง modal แดงให้ผู้ใช้เห็น

**ด่านระดับชุด — ยอดรวมของภาคต้องเท่าเป้ารวม**
`verify_send_batch()` รวมยอดต่อ SKU ของไฟล์ที่เตรียมไว้ทุกทีมในรอบเดียวกัน เทียบกับ
ผลรวมเป้าของทีมเหล่านั้น ย้ายหีบข้ามทีมได้ (I7) แต่ยอดรวมของภาคต้องเท่าเดิม
ส่วนต่างแปลว่าหีบหายหรืองอกจริง จึงไม่มี flag ให้กดข้าม

ตรวจเฉพาะ **ชุดที่มี 2 ทีมขึ้นไป** — ทีมเดียวไม่มีการย้ายหีบข้ามทีม ด่านรายทีม (ด่าน 1)
ตรวจเรื่องเดียวกันและผู้ใช้อาจกดยืนยันความต่างไว้โดยตั้งใจ ตรงนี้จึงไม่ไปตัดสินซ้ำ

และตรวจว่า SKU ที่ถูกตัดในทีมหนึ่ง **ต้องถูกตัดทุกทีมในชุด** ถ้าไม่ตรงกันจะคืน

ทุกทีม (ผ่านฟิลด์ `exclude_skus` ของ `LakehouseUploadRequest`)

**ขอบเขตการส่งบางส่วน — `brand_filter` และ `sku_filter` ใช้กติกาเดียวกัน**
ส่งเฉพาะแบรนด์ (เดิม) และส่งเฉพาะรายการ SKU (`sku_filter` — ปุ่ม「ส่งเฉพาะผลกระจายใหม่」
หลังกระจายเฉพาะสินค้าที่เป้าเปลี่ยน) ทำงานแบบเดียวกันทั้งคู่: SKU นอกขอบเขต**ไม่ถูกแตะ**
ใน Target Sun (ของเดิมคงอยู่ ยอดจึงไม่หาย) และด่าน 1 เปลี่ยนจาก "ตรวจทุก SKU ที่มีเป้า"
เป็น "ตรวจเฉพาะ SKU ที่อยู่ใน payload" — แต่ SKU ที่ส่งจริงยังต้องเท่าเป้าเป๊ะเสมอ
(`tests/test_send_sku_filter.py`) · ฝั่งกระจายมีคู่ขนานคือ `only_skus` ของ `/optimize`:
จำกัดจักรวาล SKU ก่อนคำนวณ แล้ว I1 บังคับเต็มบนเซ็ตที่เลือก (หน้าเว็บ merge ผลกลับ
เข้าตารางเดิม — SKU นอกเซ็ตไม่ถูกแตะ, `tests/test_optimize_only_skus.py`)

**ด่านที่ข้ามไม่ได้ — ยอดในไฟล์ต้องเท่าผลกระจาย**
`_assert_file_preserves_payload_totals()` เทียบยอดต่อ SKU ของ **ไฟล์ที่จะอัปโหลดจริง**
กับ payload ที่ผ่านด่าน 1 มาแล้ว ด่านอื่นตรวจตั้งแต่ก่อนแตกแถวตาม TGA grain / เติมแถวศูนย์ /
ยุบคีย์ซ้ำ / ตัดแถว ตัวเลขใน `.xlsx` จึงไม่เคยถูกตรวจเลย ส่วนต่างตรงนี้ไม่ใช่การตัดสินใจ

**สองฟังก์ชันที่ดูแลเรื่องนี้จึงยุบเฉพาะคีย์ที่ซ้ำ "ครบทั้ง 7 คอลัมน์" เท่านั้น**
`_collapse_grain_duplicate_keys()` ยุบที่ต้นทาง (รวม qty) และ `_merge_duplicate_import_keys()`
เป็นตาข่ายก่อนเขียนไฟล์ — สองแถวที่ต่างกันแค่คลังจะ**ไม่ถูกยุบ** (ผ่านออกไปเป็นคนละบรรทัด)
ทั้งคู่ **บวกจำนวนหีบเสมอ ห้ามทิ้งแถว** เมื่อเจอคีย์ซ้ำจริง เพราะยอดรวมที่ส่งต้องไม่เปลี่ยน
(`tests/test_tga_dedup.py`)

> ก่อน 7 ก.ย. 2026 ตรวจกับแคชจริงตอนพบปัญหา (คีย์ 6 คอลัมน์): 13 จาก 78 ไฟล์มีคีย์ซ้ำ,
> 1,663 คู่พนักงาน×สินค้า, ทีมที่หนักสุดหายราว 35% ของยอดทีมนั้น — เก็บไว้เป็นบริบทว่าทำไม
> ต้องมีตาข่ายสองชั้นนี้ ไม่ใช่ตัวเลขของกติกาปัจจุบัน

**ผลพวงอีกจุด — แถวที่ "สร้างใหม่" ตอนส่ง (ไม่มีคู่นี้ใน grain ของปลายทางมาก่อน) เดา
`WAREHOUSECODE` แยกจาก dim อื่น** เพราะมันไม่ใช่ "คุณสมบัติของพนักงาน" แบบเขต/ดิวิชัน
คนหนึ่งขายหลายคลังได้จริง — เดาได้เฉพาะเมื่อแถวอื่นของคนนั้นที่ปลายทางใช้คลังเดียวกันหมด
ถ้าใช้หลายคลังปนกันจะ**ปล่อยว่างไว้** ไม่ทิ้งทั้งคน (คนละกติกากับ dim อื่นที่ทิ้งทั้งแถวถ้าเดาไม่ได้)
ดูโค้ดที่ `backend/services/lakehouse.py` (คอมเมนต์ใกล้ `_dim_key_series` และจุดเดา dim
หลัง `emp_dims_from_own_grain`)

**อีกผลพวงหนึ่ง — คู่ที่ปลายทางมีอยู่แล้วแต่คลังว่างจริง ห้ามถูกทับด้วยค่าเดา** (แก้แล้ว
21 ก.ย. 2026, `1c8a74f`) ต่างจากย่อหน้าบน (ไม่มีคู่นี้ในปลายทางเลย) กรณีนี้คือคู่ที่
**มีอยู่แล้ว** และปลายทางบอกคลังว่างชัดเจน — เคยมีบั๊กที่ `_cell_str(แถวปลายทาง) or wh_req
or ""` เอาค่าที่เดามาจากประวัติขาย 2 ปีของพนักงาน (`get_warehouse_by_emp()`, ถูกแปะติดมา
กับ request ตั้งแต่ขั้นที่ 1 ทั้ง frontend `S.employees[].warehouse_code` และ backend
`employees.py`) มาทับคลังว่างจริง — Python `or` มองไม่เห็นความต่างระหว่าง "ปลายทางไม่รู้"
กับ "ปลายทางรู้แน่ว่าว่าง" ทำให้ Target Sun มองว่าเป็นคนละแถวแล้ว insert ซ้อนของเดิม
(ของจริง: SL380/SL530/SL525 ส่ง 2,651 แถว ได้คลัง `G002` ทุกแถวทั้งที่ปลายทางว่างหมด
เป้าเบิ้ล 2-4 เท่า)

**กติกาที่ถูกต้อง: ค่าคลังที่ resolve จาก grain (ปลายทาง) มาแล้วต้องเชื่อ 100% แม้จะว่าง
ก็ตาม ห้ามให้ `wh_req`/ค่าเดาจากประวัติทับอีกเด็ดขาด** — แก้ที่ `_apply_wh_hints`
(พารามิเตอร์ `trust_existing`) และ `_enrich_emp_dimensions` (gate ตาม
`skip_emp_sku_dim_merge`) ใน `lakehouse.py` **ต้องแก้พร้อมกันทุกจุดที่ `df` ไหลผ่าน**
ก่อนถึง `_build_tga_upload_dataframe` มิฉะนั้นฟังก์ชันถัดไปในสายจะยัดค่าที่ทับผิดกลับเข้ามา
ใหม่ ดูเทสคุมที่ `tests/test_destination_blank_warehouse_wins.py` และรายละเอียดเหตุการณ์
ที่ `docs/next-plan-2026-09.md` หัวข้อ 13.1

### กติกาบังคับคลังเดียว (feature ใหม่, 21 ก.ย. 2026) — จงใจสร้างแถวคนละคลังแบบควบคุมได้

**ส่งหีบ 0 ทับคลังเก่าทุกคลังของคู่นั้นในไฟล์เดียวกันเสมอ** (ตั้ง `allocated_boxes=0`

### ไฟล์เป้าราย sup ไม่ใช่แค่ cache

## ลำดับการทำงาน และใครรับผิดชอบกฎข้อไหน

```
1. _normalize_engine_inputs   → I2 (คีย์), I3 (ปัดเลข), I6 (SKU ซ้ำ)
2. _never_sold_plan           → I9  คิดแผน zero/เฉลี่ย ก่อนอะไรทั้งหมด (ถ้าเปิดกติกา)
3. _proportional              → I1, I4, I9  สร้าง baseline จากประวัติ + cap
4. _lp_optimize (CBC)         → I1, I2, I4, I5, I9  ปรับมูลค่าเงินภายในรั้ว
   └ แก้ไม่ได้ → ตกไปใช้ผลจากข้อ 3 (ตั้ง optimization_fallback=True)
5. _greedy_revenue_balancer   → I1, I2, I4, I5, I9  โยนหีบปิดช่องว่างเงินที่เหลือ
6. _enforce_even_skus_on_df   → I1  บังคับสินค้าใหม่/SKU ที่ I9 สั่งเฉลี่ยแบ่งเท่า
7. validate_allocation_vs_targets → ประตูสุดท้ายของ I1 (409 ถ้าไม่ผ่าน)
```

**ข้อควรระวังเรื่องชื่อตัวแปร LP:** ห้ามเอา `emp_id`/`sku` ไปต่อเป็นชื่อตัวแปร PuLP
PuLP ล้างเฉพาะอักขระใน `LpElement.illegal_chars = "-+[] ->/"` ซึ่งแปลง `-` เป็น `_`
ทำให้ `("A-B","C")` กับ `("A","B_C")` ได้ชื่อชนกัน → CBC พังเป็น `PulpSolverError`
→ ตกไป fallback เงียบ ๆ ใช้ `_vname()` ที่สร้างชื่อจากเลขลำดับเท่านั้น

### ก่อนแก้อะไรที่อาจทำให้ตัวเลขขยับ

```bash
python scripts/golden_allocation.py capture    # เก็บผลปัจจุบันจาก cache จริงใน data/
#   ... แก้โค้ด ...
python scripts/golden_allocation.py compare -v # เทียบ หีบทุกใบที่ขยับต้องอธิบายได้
```

harness นี้ทำงาน offline ล้วน อ่านเฉพาะ `data/target_boxes_*`, `data/target_sun_*`,
`data/hist_cache_*` ที่มีอยู่แล้ว — ไม่ยิง DAX ไม่แตะ Target Sun

> ⚠️ **ผล compare ไม่ deterministic 100%** — CBC มี time limit ต่อการแก้หนึ่งครั้ง
> (สูงสุด 60 วินาที) ทีมที่ SKU เยอะพอจะชน limit จะได้คำตอบ "ดีที่สุดเท่าที่หาทัน"
> ซึ่งขึ้นกับความเร็วเครื่องขณะนั้น รันโค้ดเดิมซ้ำจึงอาจต่างกัน 1-2 เคสได้
> (สังเกตจริงมาแล้ว: รอบหนึ่งต่าง 1 เคส รอบถัดมาตรงหมด โดยไม่ได้แก้โค้ดเลย)
>
> วิธีแยกของจริงกับ noise: รันซ้ำ — ถ้าเคสที่ต่างเปลี่ยนไปเรื่อย ๆ คือ noise
> ถ้าเคสเดิมต่างทุกรอบ หรือเคส `even`/`push` (ไม่ผ่าน LP) ต่างด้วย คือของจริง
> และไม่ว่ากรณีไหน **`sku_mismatches` ต้องเป็น 0 เสมอ** — ถ้าไม่ใช่คือกฎ I1 พัง

> **`data/` เป็น cache ที่แอปเขียนทับได้ตลอด** เป้าของทีมจึงเปลี่ยนโดยไม่มีใครแก้โค้ดเลย
> harness เก็บ "ลายนิ้วมือข้อมูลเข้า" (`inputs`: เป้ารวม / จำนวน SKU / จำนวนคน / แถวประวัติ)
> ไว้ในไฟล์อ้างอิง ตอน compare ถ้าลายนิ้วมือต่างจะรายงานเป็น
> **`[ข้อมูลต้นทางเปลี่ยน]`** แยกออกมา พร้อมบอกว่าเทียบผลลัพธ์ไม่ได้ — ไม่ใช่โค้ดถดถอย
> เจอแบบนี้ให้ `capture` ใหม่เพื่อตั้งฐาน
>
> เคสที่หายไปจาก `data/` จะขึ้น `[เคสหาย]` และทีมใหม่ขึ้น `[เคสใหม่]` — ทั้งสองอย่างปกติ
